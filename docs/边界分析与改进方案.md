## 结论摘要

1. **批量意图**：数据格式上，一次模型调用产出一份 manifest 天然支持多意图（`categories[].selections` 是数组，生成器单次运行即可全部展开）【已验证：generator.js 的 expandGraph 遍历全部 selections】。但"能装下"不等于"装得对"——意图数量 ≥3 时，推荐**两段式调用链**（1 次路由 + N 次并行填充 + 1 次确定性合并 + 1 次代码生成）。三个"单次"必须区分：**单次模型调用 ≠ 单次业务请求 ≠ 单次代码生成**（定义见 1.1）。
2. **覆盖范围**：50 种方法中 **10 种已实现（全部为"已覆盖但实现简化"）**，40 种仅清单条目级存在（部分覆盖），**没有任何方法达到"完整覆盖"**——因为切片从未经过真实 MDK 编译验证，也没有资源文件生成与运行期验收。你提的 16 个待补充主题：**10 个未覆盖、3 个部分覆盖（#49 JEI、#43/44 维度、#31/34 实体 AI 的条目在 50 清单里但无实现）、2 个与已实现内容重叠（方块实体=已覆盖但简化、网络同步=部分覆盖）**。
3. **当前两大不足**：① 加工站进度只走 `ContainerData`（仅整型、仅服务端→客户端、仅 GUI 打开期间），切片场景够用（严重度低），复杂机器（GUI 按钮、能量数值、事件推送）必须引入独立 Packet（严重度中高）；② 实体资源防错乱机制**完全不存在**（实体类 5 个插座全空，无任何资源生成），相关风险全部是前瞻性的，但一旦上实体类就是高危项。
4. **组织方式**：不建议继续"一方法一示例"扁平化。建议改为**四层**（意图路由层 7 类保留 / 套路插座层 50 法扩展 / 能力层 energy·networking·config·sync / 资源层 assets·datagen）+ **组合配方（bundle）** + **模板 partial 与 capability 注入点**，现有 requires/derive 机制无需重写。
5. **验收体系**：把 50 清单机器化为 `methods.json`，新增 `scripts/coverage-check.js` 做"状态 ↔ socket ↔ 模板 ↔ 示例 ↔ 测试结果"五向交叉核查 + "关键实现标志" grep（防"只有名字没有实现"），编译/运行验收用占位符【测试结果】挂账。

## 1. 批量方块/实体意图识别边界

### 1.1 三个"单次"的定义（先统一口径）

| 概念 | 定义 | 现状 |
|---|---|---|
| 单次模型调用 | 一次 LLM completion，输出一份结构化 JSON | 【已验证】意图识别层**不存在**，无任何 LLM 调用代码；manifest 目前是手写的 |
| 单次业务请求 | 用户一句话 → 完整流水线（识别→拆分→路由→合并→生成）一次性走完，内部可含多次模型调用 | 【建议】尚未实现 |
| 单次代码生成 | 合并后的 manifest 交给 generator 跑一次，确定性产出全部文件 | 【已验证】已支持：单次运行可处理多个分类、多个选择（expandGraph 遍历全部 selections；hub 用 `{{#each}}` 聚合多实例） |

关键差异：**"单次代码生成"是最容易达成的，引擎层面已经具备**（多选择单次展开、hub 聚合都有代码佐证）；真正未解决的是"单次业务请求"里模型侧的可靠拆分。

### 1.2 单次模型调用能否完成批量识别

**结论：能，但可靠性与意图数量负相关。**

- 数据格式天然支持：manifest 的 `categories[].selections` 是数组，一份 JSON 可以装下任意多个意图【已验证：schema/manifest.schema.json + expandGraph 实现】。
- 可靠性来源（现有机制可直接复用）：socket id 是**封闭枚举**（50 个），选项是**有限档位**（choice），且你设计的"+终止"要求模型对每个分类显式表态（"选项就是具体分类里面的具体行为+终止"，你的原文）——这天然抑制漏识别：模型必须对 7 个分类逐一给出"选了谁/终止"。
- 风险随意图数增长的原因【推断】：长 JSON 生成中后段意图容易被前段内容"稀释"；多个意图共享相似注册名时容易张冠李戴；单次输出一旦局部错误，需要整份重来，重试成本高。

**推荐策略**：
- **意图数 ≤ 2**：单次模型调用直接输出整份 manifest（schema 约束 + 封闭枚举），生成器单次运行。
- **意图数 ≥ 3 或涉及 3 个以上分类**：两段式（见 1.3）。

### 1.3 推荐调用链（两段式）、重试条件、合并机制

```
用户需求（一句话）
  │
  ▼
[调用1 路由]  输入：需求原文 + 7 类目录摘要 + socket 封闭枚举
             输出：{ intents: [{category, 描述, 关键名词}],
                    categoryDecisions: { 7类: selected | terminated } }
  │  ← 强制 7 类全覆盖判定（漏识别的第一道防线）
  ▼
[调用2..N 填充] 每个 selected 分类并行一次调用
             输入：该分类的 socket 清单 + 参数档位 schema + 需求中该分类的原文片段
             输出：该分类的 selections + params（schema 约束）
  │
  ▼
[确定性合并器（无模型）]  键 = (分类, 注册名/类名) 去重：
             同键同参 → 保留 1 份（幂等）；
             同键异参 → 转仲裁调用（注入冲突上下文）；
             分类-插座不匹配 / 必填参数缺失 → 转重填调用；
  │
  ▼
[generator 单次运行]  → 全部 Java 文件 + ASSEMBLY.md 派生链
```

- **重试条件**（每次重试注入具体错误信息，最多 2 次）：JSON 解析失败；schema 校验失败；分类与插座不匹配（现有 expandGraph 已能报"插座不属于分类"【已验证：lib/graph.js 分类校验】）；必填参数缺失/档位非法（guard 已能报【已验证：lib/guard.js 参数校验】）；派生失败（选了 A 缺 B，expandGraph 已能报【已验证】）。
- **语义冲突（同键异参）→ 仲裁调用**：只在合并阶段出现，把冲突双方和需求原文交给模型选边，禁止合并器自己拍板。
- **结果合并机制**：合并器是纯确定性代码（可单测）；合并产物是版本化 manifest；每次生成输出 `ASSEMBLY.md`（含每个插座"显式/由谁派生"链）【已验证：generator.js 已输出该报告】→ 满足"多步骤可追踪、可复现"。

### 1.4 漏识别 / 误识别 / 重复处理 的防护

| 风险 | 防护（已有哪些 / 建议新增） |
|---|---|
| 漏识别 | 【已有】"+终止"强制 7 类全覆盖表态；【建议】路由输出要求附"需求原文引用片段"，审计可回溯 |
| 误识别 | 【已有】socket id 封闭枚举 + 分类归属校验（expandGraph）+ 参数档位校验（guard）；【建议】填充调用输入只给"该分类的选项"，缩小选择面（Jev 式小选项集） |
| 重复处理 | 【已有】guard 的 collisionGroup 能在生成期**报错**（guard.js:110）；【建议】批量场景下"报错"应前置为合并器"幂等去重"（同键同参合并、异参仲裁），generator 报错保留为最后防线 |

## 2. 覆盖范围评估

### 2.1 判定标准（四级定义，可机器校验）

| 状态 | 判定标准（须同时满足） |
|---|---|
| **完整覆盖** | ① catalog 有 socket 且 requires/references/params 完整；② 模板生成代码；③ 在真实 1.20.x MDK 中 `gradlew build` 通过（有【测试结果】记录）；④ 该方法所需资源文件（assets/data）由生成器产出；⑤ ≥1 个示例 manifest + ≥1 条运行期行为断言 |

### 2.2 该标准如何被实际校验（不靠名称比对）

## 3. 当前实现不足核查

### 3.1 ContainerData 同步的边界

**现状事实**【已验证：templates/sockets/block-entity.java.tpl、menu.java.tpl】：
- 进度同步 = `ContainerData`（progress / maxProgress 两个 int）+ Menu `addDataSlots(data)`；
- 方块状态变化 = `sendBlockUpdated` + `getUpdateTag()` / `getUpdatePacket()`（标准 update-tag，非手写包）；
- **不存在任何 Packet 类文件**（13 个生成文件里没有 network 相关内容）。

**不足场景与何时必须手写 Packet**：

| 场景 | ContainerData 可行？ | 说明 |
|---|---|---|
| 进度条（int 0..N） | ✅ 够用 | 当前加工站就属于这档 |
| 客户端→服务端操作（GUI 按钮、配方选择、排序） | ❌ 完全不行 | ContainerData 是单向的，且仅 GUI 打开期间同步 |
| 非整型数据（能量数值浮点、文本、ItemStack 预览、任意 NBT） | ❌ 不行 | ContainerData 只能装 int |
| 事件式推送（机器完成提示音/通知/粒子） | ⚠️ 勉强 | update-tag 会整包重发，粒度粗、频率高时浪费带宽 |
| 多人同步语义（每玩家独立状态、进度动画重放） | ⚠️ 边缘 | 依赖 GUI 生命周期，GUI 关闭即断 |

- **影响范围**：切片内仅进度条，影响面小；**触发条件**是任何 GUI 交互回传或非整型展示；**严重程度**：切片=低，复杂机器=中高。
- **建议方案**：新增 networking 能力插座：`Network.java`（SimpleChannel 注册 + 协议版本参数）+ C2S/S2C 包模板（encode/decode/handle）+ BE 模板注入同步方法；`requiredMarkers` 定为 `SimpleChannel`、`registerMessage`、`encode`、`handle`。
- **验证方法**：① 生成期包 ID 冲突检查（复用 collisionGroup 机制）；② 编解码 round-trip 单测；③ 运行期验收：点击按钮 → 服务端状态变化 → GUI 刷新断言（记录进【测试结果】）。

### 3.2 实体资源错乱/重复风险（前瞻性评估）

**现状事实**【已验证：catalog.json 分类 5 "entity" 的 sockets 为空数组】：实体类 8 个方法（31-38）零实现，无实体模板、无资源生成。因此下述风险**当前全部是潜在风险**（尚未发生），但实体类一旦开工即为高危项。

| 风险 | 影响范围 | 触发条件 | 严重程度 | 建议防护【建议】 | 验证方法 |
|---|---|---|---|---|---|
| 重复注册（两个实体同 registryPath） | 运行时注册崩溃/后者覆盖 | 批量意图中两个实体同名 | 高 | 复用 guard 的 collisionGroup 机制，扩展到实体注册名 | 负例 manifest 跑 generator 必须报错（单测） |
| 资源路径冲突（同 texture/geo/animation 路径） | 资源互相覆盖、模型找错文件 | 两实体命名近似（如 wolf/wolf2） | 高 | 生成器维护 **asset 路径所有权表**，生成期冲突即报错 | 生成后资源清单 diff 无重复；负例测试 |
| 客户端/服务端不一致（渲染器/模型层单端注册、动画定义缺客户端） | 服务端类加载失败、白模、崩溃 | 模板把 client-only 类写进公共注册段 | 高 | catalog socket 增加 `side`（common/client/server）字段；guard 静态检查 client-only 类只出现在客户端注册段 | 编译 + 双端启动冒烟（【测试结果】） |
| 数据持久化错位（save/load 键漂移） | 数据丢失/字段错位 | 手动改模板时两侧不同步 | 中 | 实体数据字段由统一 params **单一来源**生成 save/load 两侧，禁止手写；生成器内置键集合自检 | 单测断言 write 键集合 == read 键集合 |

### 3.3 风险总清单（含意图层）

## 4. 整体改进方案

### 4.1 优先级与融入方式

| 优先级 | 内容 | 理由 | 依赖 | 融入方式 |
|---|---|---|---|---|
| P0 | 配置系统、网络包、能量能力 | 所有"机器类"套路的公共地基，复用价值最高 | 26 号方块实体 | 能力层插座，被 block-entity require，模板注入点填充 |
| P1 | 附魔、状态效果/药水、流体注册、命令、按键绑定、HUD | 注册/行为独立性强，可并行 | registration 类扩展 | 各自独立插座，挂入对应 7 类 |
| P2 | 实体系统（31-38）+ 资源防错乱机制 | 16 号主题的前置；防错乱机制随实体一起落地 | 3.2 的 side/asset 表 | entity 类插座 + 资源层 |
| P3 | JEI 兼容（#49 实现）+ Curios/Patchouli | 兼容层生态价值 | 依赖探测机制 | compat 插座组 |
| P4 | 多方块、维度/世界生成进阶（ChunkGenerator/密度函数） | 重器，工程量最大 | 方块实体持久化、datagen | worldgen + multiblock 插座 |

每项落地时的最小交付集（以 P0 网络包为例）：
- **最小可运行示例**：加工站 GUI 加一个按钮，点击清空输出槽（C2S）+ 进度完成时 S2C 通知；
- **配置项**：协议版本、包 ID 前缀、消息枚举（choice）；
- **注册步骤**：Network 类在模组构造器中注册（主类钩子）；
- **资源文件**：无（纯代码）；
- **测试场景**：单测 encode/decode round-trip + 双端启动 + 按钮行为断言；
- **验收标准**：requiredMarkers 命中 `SimpleChannel`/`registerMessage`/`encode`/`handle`；【测试结果】记录编译与行为断言通过。

### 4.2 组织方式重构：放弃"一方法一示例"

50 法扁平化"一方法一示例"的代价：注册类方法与行为类方法重复大量样板（每个 GUI 机器都要重写一遍能量/配置/网络）。建议四层：

1. **意图路由层**：7 大类保留（你的分类粒度已被证明适合路由，"+终止"机制继续用）；
2. **套路插座层**：50 法扩展为"注册/行为"插座（现有机制直接承载）；
3. **能力层**：energy / networking / config / sync 等横切插座，通过 requires 被套路插座引用，模板预留 `{{#if hasNetworking}}` 注入点（现有 render.js 的 #if 已支持【已验证】）；
4. **资源层**：assets / datagen 插座（防错乱机制挂在这层）。

复用机制【建议】：
- **组合配方（bundle）**：`machine = block-with-gui + block-entity + energy + networking + config`，manifest 选 bundle 即展开——只需在 catalog 加 bundle 定义（requires 宏），**不需要改引擎**；
- **模板 partial**：render.js 增加 `{{> partialName}}` 语法（【建议，未实现】，当前引擎只有 if/each 系）；
- **方法清单索引化**：`methods.json` 承载 50+清单与状态、requiredMarkers、side、依赖，catalog 之外单独演进。
